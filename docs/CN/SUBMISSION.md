## 1. 摘要

我们构建了一个由大语言模型驱动的智能体，在 KuaiRand-Pure 用户内短视频排序基准上运行完整的机器学习研究闭环：
它先复现官方基线，说明自己观察到的瓶颈，提出一个实验，修改真实的模型代码或配置，**在训练之前先对该改动进行验证**，
随后训练、评估，并通过**配对的用户级自助法（bootstrap）**与对照组比较，决定下一步要研究什么，组装一个互补的模型组合，
写出一份经过校验的提交结果——直到触发**主办方自己定义的收敛规则**才会停止。

**实测结果**（`runs/run_20260831_090457`，Gemini 实时运行，共执行 4 次实验，耗时 450 秒，消耗 12,593 个 token）：

| 指标 | 数值 |
|---|---|
| FM 基线 | 0.60147 |
| 发现的最佳单模型 | 0.60366 |
| 模型组合，在全部验证集上调参 —— *偏乐观，样本内估计* | 0.60463 |
| **模型组合，诚实的 5 折用户级交叉验证** | **0.60409 ± 0.00141**（相对 FM **+0.00259**） |
| 停止原因 | `official_convergence`（ε=0.002，N=3） |
| 提交结果 | 通过了冻结版 `submit.py --check` 的校验 |

**我们对外报告的数字是 0.60409 ± 0.00141，而不是 0.60463。** 系统自己就会把较大的那个数字标记为"经过调参、样本内"，
并实测出这种乐观偏差的大小（约 +0.0007），而不是假装它不存在。

**我们最引以为豪的结果，恰恰是一个被否决的结果。** 智能体的"行为感知历史"实验一度显示出 **+0.0165** 的提升——
是实测噪声下限的十八倍。团队没有直接采信这个数字，而是认定这样的量级不合常理，深入排查了其机制，
发现了一个训练/线上评估不一致的问题，在诚实的策略下重新构建了该实验，结果变成了 **−0.00167**。
这个所谓的突破被否决了，该功能**默认以禁用状态交付**（见第 10 节）。

## 2. 挑战题目

赛道二要求智能体自主运行如下闭环：

```
理解问题 → 形成假设 → 修改流水线/代码 → 训练 → 评估
  → 解读结果 → 决定下一个实验 → 重复 → 选定最终方案
```

**内部任务。** 对每个用户，按 `long_view`（观看完成度信号）对*该用户自己*的曝光记录进行排序。
`主指标 = ½(GAUC + nDCG@5)`。官方 FM 基线：验证集 0.6016 / 测试集 0.5946。

**两个决定一切的事实。** 理论上限**约为 0.86，而非 1.0**（27.1% 的测试用户全部为负样本，9.2% 全部为正样本——
无论哪个模型都无法改变他们的 nDCG），配对验证噪声下限为 **σ ≈ 0.0009**。因此真正的提升是以千分之一为单位度量的，
一个分不清信号与噪声的智能体，会自信满满地追逐自己的方差。

## 3. 为什么这是一个自主的机器学习研究者，而非 AutoML 脚本

AutoML 脚本只是在超参数网格中搜索。而这个智能体做了六件网格搜索做不到的事：

| 行为 | 具体表现 |
|---|---|
| **先陈述问题，再提出方案** | `Hypothesis.problem_identified` 是必填字段，且*最先*被写出 |
| **编写并采纳真实代码** | 重写六个代码块之一，或整体切换模型族；每次改动都会被快照并计算哈希 |
| **拒绝编造** | 被要求实现位置偏差塔时，它回复该数据集中根本不存在位置特征——而它**确实说对了**，数据里没有这一列 |
| **用统计方法解读结果** | 每个节点都会用配对的用户级自助法与对照组比较；驱动结论的是 `P(Δ>0)`，而不是一个原始差值 |
| **从负面结果中学习** | 一次 `rejected`（被拒绝）的结论会改变它下一步的提案；负面证据同样是一等公民 |
| **权衡多样性，而不只是精度** | 即便某模型的独立表现更差，只要其误差与其他模型不相关，它依然会被保留 |

还有一件大多数智能体都做不到的事：**当结果的量级不合常理时，它会怀疑自己迄今为止最好的成绩**（见第 10 节）。

## 4. 端到端的自主研究闭环

```
观察 → 提出假设 → 制定计划 → 编码 → 护栏检查 → [调试] → 训练 → 评估
  → 对比 → 反思 → 决策 → 下一个实验 → 组合集成 → 收尾定稿
```

三个大语言模型角色作为一套确定性策略之上的算子：**Proposer 提议者**（该攻克什么问题）、
**Coder 编码者**（如何在一个代码块内实现它）、**Reflector 反思者**（为什么失败、如何恢复）。
搜索策略采用带 ε 探索阀的最佳优先搜索——刻意不用蒙特卡洛树搜索（MCTS），因为每个节点都对应一次真实的训练，
而这个基准合理情况下在约 4–6 次实验后就会结束，样本量太少，不足以支撑可靠的价值估计。

每一步都会产生一条结构化、可审计的事件记录。演示中的内容没有一句是旁白解说。

## 5. 信任与完整性架构

这是我们最希望技术评审仔细审查的部分。

**一个冻结的信任边界。** 五个文件——`data.py`、`evaluate.py`、`submit.py`、`pipeline/run_node.py`、
`pipeline/contracts.py`——都经过 SHA-256 哈希锁定，并在每次运行开始时校验。智能体永远无法（无论是不小心还是通过一次
臆造的"修复"）修改分数所依赖的代码。开发过程中新增的每一项能力都绕开这条边界运作，而不是穿过它。

**分层的隐藏集保护——以及一个关于它的诚实声明。** 我们发现自己早期的文档曾声称获取标签"在物理上是不可能的"。
事实并非如此。隐藏测试集标签，以及辅助的 `is_click` 列，其实就存放在每个代码块都能访问到的目录里，
**仅凭 `is_click` 对验证集排序就能拿到 0.7466 分——相当于基线之上全部提升空间的 58.8%，且完全不需要训练。**
这个漏洞现已通过五层机制被彻底堵上（独立的隐藏集目录、加载器拒绝访问、构建期断言、静态读取护栏、合理性警报），
文档中的相关表述也已改写为真实情况。这一点很重要：METR 的研究观察到，在 RE-Bench 的 128 次智能体运行中，
有 39 次出现了明显的"奖励破解"（reward hacking）行为，且事先并未提示智能体作弊。

**配置有效性校验。** 一个挂载的模型根本读不到的旋钮，会在训练*之前*就被拒绝，而不是悄悄地训练出一个基线结果。
这一机制修复了一个此前存在的缺陷——它曾把本项目中最有效的干预手段，变成了一个被误判的"无效"结果（见第 9 节）。

**溯源记录。** 每个节点都会记录*预期*执行的改动与*实际*执行的改动，附带每个代码块的源码哈希、缓存版本
与代码状态哈希——因此任何结论都不会建立在"智能体的提案就是实际运行内容"这一未经验证的假设之上。

## 6. 科学方法论

| 原则 | 实现方式 |
|---|---|
| 区分三种方差 | 训练随机性（FM/LightGBM 为 0.00000，DIN 约为 σ≈0.00025）、**验证样本噪声**（σ≈0.0009）与跨随机种子的泛化差异——三者从不混为一谈 |
| 只降低真正制约结论的那部分方差 | 对已保存的预测结果做**配对用户自助法**（约 2 秒，无需重新训练），专门对付验证噪声；多随机种子的*重新训练*仅用于随机性模型确有必要度量训练噪声的场合 |
| 证据不等于采纳状态 | 一个节点可以是当前冠军，同时仍是 `inconclusive`（不确定）；也可以独立评估为 `rejected`（被拒绝），却仍是模型组合中的有效成员 |
| 结构上就诚实的报告 | 调参后的样本内估计，与经交叉验证的估计，在每份报告中都是两个独立字段 |
| 尊重多重比较问题 | 12 次检验中有一次 P=0.91，我们明确**不会**把它当作一项发现来报告 |
| 拒绝汇总不可比的证据 | 跨运行汇总证据要求缓存版本*与*代码状态哈希同时一致 |

## 7. 一次真实研究轨迹示例（原样摘录自实际运行）

```
根节点  复现官方 FM 基线                                        0.60147
第1次  A  "将损失函数改为 BPR，以优化成对排序"                  0.60361  已确认  P(Δ>0)=1.00
第2次  D  "改用 LightGBM 作为模型族"                            0.60205  已拒绝（独立评估）
         → 但排名相关性仅 0.860，是最不相关的成员 → 仍被保留为模型组合候选
第3次  B  "改用带 BPR 损失的 DIN 模型族"                        0.60366  不确定  P(Δ>0)=0.52
第4次  —  提案在训练前被判定为"结构性空操作"而拒绝 → 重新提出
第4次  C  "加入辅助任务（点击与点赞）"                          0.60247  已拒绝
         → 排名相关性 0.974，边际组合贡献 +0.00000 → 冗余，未纳入模型组合
停止    official_convergence（ε=0.002，N=3），共执行 4 次实验（上限为 50 次）
```

*已拒绝*，同时又将其保留为模型组合的有效成员——这是两个不同的问题，系统对它们分别作答。

## 8. 结果

### 诚实估计 vs 调参估计

| 估计值 | 数值 | 含义 |
|---|---|---|
| `final_valid_tuned` | 0.60463 | 混合权重是在*同一批*被用来评估的用户上调出来的——**偏乐观** |
| **`final_valid_honest`** | **0.60409 ± 0.00141** | 对*整套组合流程*做 5 折用户级交叉验证——这才是站得住脚的数字 |
| 相对最佳单模型的交叉验证提升 | +0.00064 ± 0.00051 | 大致一个标准误：真实、一致，但幅度不大 |

我们直接测量了这种乐观偏差的大小：在八次随机的用户切分中，权重选择带来的乐观偏差平均为 **+0.00072**，
大约相当于一个朴素报告的集成提升量的一半。

### 与基线的对比

| 模型 | 验证集主指标 | 数据来源 |
|---|---:|---|
| 随机 | 0.4834 | `baseline_scores.json` |
| 物品热门度 | 0.5807 | `baseline_scores.json` |
| **FM（官方基线）** | **0.60147** | 由我们的根节点精确复现 |
| FM + BPR（被发现的干预手段） | 0.60361 | +0.00214，P(Δ>0)=1.00 |
| 最佳单模型（DIN） | 0.60366 | |
| **智能体模型组合，诚实估计** | **0.60409 ± 0.00141** | **相对 FM +0.00259** |
| 理论上限 | 0.8484 | |

### 模型组合的贡献——最有意思的部分

| 成员 | 独立表现 | 排名相关性 | 边际贡献 |
|---|---:|---:|---:|
| FM + BPR | 0.60361 | 0.906 | **+0.00229** |
| **LightGBM** | **0.60205**（*较弱*） | **0.860**（*最不相关*） | **+0.00050** |
| DIN | 0.60366（*单模型最佳*） | 1.000 | +0.00040 |
| FM + BCE（根节点） | 0.60147（*最弱*） | 0.852 | +0.00017 |
| DIN + 辅助任务 | 0.60247 | 0.974 | **+0.00000**（*冗余*） |

**一个较弱的模型，价值可能超过一个较强的模型。** LightGBM 凭借与其他模型不相关的误差，
在独立分数不及冠军的情况下依然拿到了模型组合的一席之地；而那个带辅助头、独立分数*更高*的节点，却毫无贡献。
如果只按独立分数选型，选出来的会是错误的模型。

### 稳健性与故障恢复

`python -m agent.run --faults` 会向某个代码块注入一次崩溃。Reflector（反思者）会修复它，节点重新运行——
值得注意的是，恢复后的节点会被判定为 **`no_effect`（无影响）**，因为修复后的代码块在功能上与其父节点完全等价。
恢复机制生效了，*同时*系统也拒绝把它记录为一项科学发现。整次运行最终仍会完成一份有效的提交。
本项目至今没有出现过运行崩溃的情况。

### 资源消耗（可行性）

| | 实时运行 |
|---|---|
| 已执行实验数 | 4 次（上限 50 次） |
| 总耗时 | 450 秒（上限 6 小时） |
| LLM token 消耗 | 12,593 |
| 人工干预次数 | 0 |

**我们不会刻意把配额用满。** 按主办方的规则，一次健康的运行大约在 4–6 次实验后就会收敛；
次数上限与耗时上限是限制，不是目标。工程上的目标是让这寥寥几次实验都货真价实，而不是硬凑出更多次数。

## 9. 创新点

1. **配置有效性校验。** 我们发现，一个提出的旋钮参数可能被挂载的模型悄悄忽略——一个"使用 BPR"的假设实际训练的却是
   普通 BCE 损失，返回了一个与基线字节相同的结果，在记录在案的 21 次运行中出现了 4 次。
   智能体把它记录为"BPR → 0.6015，已拒绝"，而它自己的记忆此后就一直告诉它不要再尝试这个本来最有效的干预手段。
   修复这个问题后，直接找回了 **+0.00214** 的提升。"预期的干预 ≠ 实际执行的干预"这一普遍教训，
   如今已成为每次实验都会校验并记录的属性。
2. **证据与记账逻辑分离。** 科学结论来自配对自助法，而不是"某节点是否比其父节点高出一个随意设定的门槛"。
   在此之前，智能体的记忆曾把自己表现最好的模型标记为"REJECTED——不要重复"。
3. **考虑模型组合价值的评估。** 排名相关性、成对混合增益与留一法边际贡献，均直接基于已保存的预测结果计算——
   无需重新训练——并呈现给 Proposer（提议者），因此一个"多样但较弱"的模型会被当作一次成功，而不是失败。
4. **诚实的集成估计。** 对*整套组合流程*做 K 折交叉验证，四种数据角色（选择成员／调整权重／报告／重新拟合）
   从不混用。
5. **保持模型身份一致。** 测试集预测来自那个驱动了选型决策的、同一个已训练模型实例的验证集预测。
   对随机性模型而言这一点很重要：同一个 DIN 配置训练两次，排名相关性也只有 0.926。
6. **用低成本分析替代高成本的重新训练。** 自助法、相关性计算与混合评估，在已保存的预测结果上只需几秒钟；
   多随机种子重新训练只花在训练噪声本身确实是待研究问题的场合。

## 10. 自我修正：被否决的突破

**这是"这是一个研究智能体，而非排行榜刷分器"最有力的证明。**

**假设。** 在自动连播的短视频信息流里，"划走"是有意义的负向证据，而"曝光"本身并不等于正向反馈——
这一机制在文献中有直接支持（RecSys'23）。我们的 DIN 此前只把历史记录看作一串视频 ID：一个被划走的视频和一个被
喜欢的视频看起来毫无区别。于是我们给每条历史记录都加上了一个反馈状态。

**表面上的结果。** 带反馈状态的 DIN 得分 **0.61925**，不带则为 **0.60275**，三次配对重复训练一致显示：
**+0.0165，P(Δ>0) = 1.00。**

**保持怀疑。** 这个基准上其他任何一个干预手段带来的提升都在 0.002 左右。仅仅多了一次嵌入查找，
效果却是实测噪声下限的十八倍——这不像是一个合理的建模收益，更像是一个症状。团队没有直接采信这个结果，而是深入排查。

**诊断。** 反馈信息的覆盖率是不对称的：

| 数据切分 | 模型能看到结果的历史事件占比 |
|---|---:|
| 训练集 | 100.0% |
| **验证集** | **100.0%** |
| **测试集** | **75.8%** |

验证集中的一行，可以看到*更早的验证集行*的结果。而测试集的一行看不到——因为一次提交是把所有测试集行一次性打分，
中间没有反馈。**这个提升在用于选型的数据集上结构性地存在，却在真正会被打分的数据集上结构性地不存在。**
它本会污染这次运行中的每一个选型决策，而在测试集上却什么也带不来。

**重建。** 我们修改了策略，规定只有*训练窗口内*的结果才可以成为特征，从而让验证集与测试集在这一点上对称。
在这一诚实策略下：

| 实验分支（3 次配对重复） | 相对无反馈版本的差值 | P(Δ>0) |
|---|---:|---:|
| DIN + 反馈状态 | **−0.00167** | 0.00 |
| DIN + 反馈状态 + 反馈随机丢弃 | **−0.00070** | 0.14 |

诊断出的补救方案（在训练时对状态做掩码，使其与推理时保持一致）挽回了 58% 的损失——**证实了背后的机制**——
但这个干预手段终究没有带来正向收益。用模型组合的多样性也无法挽救它（排名相关性 0.942，混合增益 +0.00002）。

**结论。** 一个有文献支持的假设，一个表面上高达 18 倍噪声下限的胜利，最终却是一个**负面**答案。
`use_fb` **默认以禁用状态交付**。我们自己的路线图文档中曾预测这会是本项目最大的一个提升点；
这个预测被证伪了，我们选择直接修正文档，而不是为它争辩。搞清楚真相的总成本：大约四分钟的 GPU 时间。

## 11. 当前局限

坦率说明，因为这些正是评审最应该首先追问的问题。

* **每一个数字都是验证集侧的。** 诚实的交叉验证估计校正的是权重调参带来的乐观偏差，而不是验证集到测试集的分布漂移。
  按设计，测试集表现是未经测量的。
* **相对基线的提升，绝对值很小**（诚实估计为 +0.0026）——但理论上限是 0.8484，噪声下限是 0.0009，
  这个区间本来就很窄，是性质使然。
* **当前验证集无法分辨小于约 0.002 的效应。** 若干悬而未决的问题（所有辅助任务分支）是因统计功效不足而无法定论，
  而不是设计上的缺陷。
* **跨运行证据目前是空的。** 兼容性护栏正确地拒绝了在缓存/代码发生变更后，汇总此前 14 条历史记录——
  这个判定是对的，但也意味着这套跨运行记忆机制目前还没有真正发挥作用。
* **随机曝光度量目前只覆盖 FM 模型族**；DIN 与 LightGBM 还需要各自的配套缓存。
* **`max_llm_usd` 参数已声明但尚未强制执行**——目前没有硬性的 LLM 花费上限。
* **重复次数偏少**（n=2–3），是 DIN 与辅助任务相关测量结果的基础。
* **单次实时运行按设计是短的**（4 次实验）。这是主办方收敛规则在正常发挥作用，不是智能体半途而废——
  但这确实限制了单次运行所能承载的科学探索量。

完整的工程局限列表见 [SYSTEM.md 第24节](SYSTEM.md#24-已知的工程局限)。

## 12. 可复现性

以下确定性路径不需要 API key、不需要联网、也不需要 GPU。

```bash
python -m agent.run --smoke     # 精确复现 FM 基线（0.60147）+ 校验 frozen.lock
python -m agent.run --mock      # 完整研究闭环的离线版本，由脚本驱动的算子
python -m agent.run --faults    # 注入一次崩溃，验证恢复机制，仍能完成一份有效提交
python -m tests.test_stats      # 自助法与冻结版评估器的误差小于 1e-5
python -m tests.test_blockspec  # 旋钮生效契约，含运行时的逐位一致性校验
python -m tests.test_leakage    # 隐藏集隔离；恶意代码块会被拒绝
python -m tests.test_orchestration  # 收敛语义、去重、"证据 ≠ 状态"
python -m tests.test_sequence   # 时间顺序 + 反馈状态泄漏安全性
```

一次实时运行需要 `GEMINI_API_KEY`（或 `.env.local`）：

```bash
python -m agent.run
```

**关于 `--mock` 的诚实说明。** mock 路径回放的是 `tests/mock_moves.py` 中*预先写好脚本*的算子动作。
它"0 次人工干预"这一点对机制本身是成立的，但其中的研究决策是脚本设定好的，并非自主产生。
**本文档中的每一个头条数字，都来自一次 Gemini 实时运行**（`runs/run_20260831_090457`），
其中的假设、代码改动与决策都是模型自己做出的。设置 `--mock` 的意义在于：让包括完整性护栏与恢复路径在内的
整个流程，可以在不需要 API key 的情况下确定性地被验证一遍。

每次运行都会写出 `run_log.jsonl`（按节点）、`events.jsonl`（按研究事件）、`resource_report.json`
（资源记账 + 调参估计 vs 诚实估计的结果），以及一份通过 `submit.py --check` 校验的提交结果。

## 13. 研究控制台与演示

**这是一套展示基础设施，而不是一项模型改进。** 控制台渲染的是智能体实际产出的记录；
它从不模拟执行过程，也从不自行计算任何指标。

```bash
python -m agent.console_server        # http://127.0.0.1:8712/
```

* **▶ 回放** —— 以 1×–12× 速度确定性地回放一次已完成的运行。不需要 API key、网络或 GPU，
  因此录制内容不会受实时时序影响。
* **◉ 实时** —— 轮询一个正在运行中的智能体，实时推送新事件。

状态栏刻意把两组容易被混为一谈的概念区分开：**官方**收敛状态 与 内部研究记账；
以及**已执行的实验** 与 提案尝试次数。

### 建议的 4 分钟演示流程

以 2× 速度回放 `run_20260831_090457`：

| 时间 | 要点 |
|---|---|
| 0:00–0:20 | 运行开始；冻结边界校验与隐藏集隔离作为真实的护栏事件出现 |
| 0:20–1:20 | 观察 → BPR 假设 → 有效的干预 → 训练 → `P(Δ>0)=1.00 已确认` |
| 1:20–2:10 | LightGBM：独立评估**被拒绝**，但排名相关性仅 0.860，因此仍作为模型组合候选被保留 |
| 2:10–2:40 | 一个提案被识别为结构性空操作，**在训练前就被纠正** |
| 2:40–3:20 | 模型组合面板：独立表现最弱的成员，拥有最大的边际贡献 |
| 3:20–4:00 | 官方收敛判定、诚实的交叉验证估计、提交结果通过校验 |

如果时间允许，最值得展示的一幕是第 10 节——那个被智能体自己否决的 +0.0165 结果。
